# Postmortem: home lab cluster setup took 4.5 hours instead of one evening

**Date:** 2026-10-10
**Status:** Draft
**Format:** Blameless

## Summary

Building the Proxmox host and a 3-node kubeadm cluster was planned as one evening of work and took about 4.5 hours (15:30 to 20:00). There was one dominant root cause: **the home network has no IPv6 connectivity, but the Proxmox host, the VMs and containerd all preferred IPv6 when a server offered it.** That showed up as a failed download on the host, slow image pulls in Kubernetes, and nodes stuck `NotReady`. Several smaller issues (a wired-network requirement, a typo, a background apt process, a broken repo line) added time. The cluster ended healthy with all three nodes `Ready`.

## Impact

- About 3 hours of extra setup time.
- Worker nodes `NotReady` for about 20 minutes.
- No data loss. This was a new, empty lab.

## Root cause

The ISP connection provides IPv4 only, but hosts learn IPv6 addresses for servers through DNS (AAAA records). Tools try IPv6 first. Some fail fast with "network unreachable" (`wget`); others wait for timeouts before falling back, which made downloads slow rather than broken. That made the problem look like several different issues.

containerd is written in Go and ignores the system's `/etc/gai.conf` address preference, so the fix that worked for the host's tools did not help Kubernetes image pulls. That required disabling IPv6 on the nodes with a sysctl.

**Follow-up at 19:57: the mitigation caused a new failure.** `net.ipv6.conf.all.disable_ipv6 = 1` also disables IPv6 on the loopback interface, so `::1` stopped existing. The API server talks to itself over loopback and tried `[::1]:6443`, so creating a namespace failed with "cannot assign requested address". Fix: keep IPv6 on loopback with `net.ipv6.conf.lo.disable_ipv6 = 0`. A good reminder that every mitigation is a change, and changes need their blast radius checked.

## Contributing factors

- **Guide examples didn't match the network.** It used 192.168.1.x; the TP-Link router uses 192.168.0.x.
- **Unstated prerequisite.** The guide did not say up front that Proxmox needs a wired connection.
- **Shell variables across copy-paste.** `$KUBE` was empty when the repo line was written, which produced a malformed file instead of a clear error.
- **Template errors multiply.** A typo in the template's network bridge reached all three clones.
- **First-boot background work.** cloud-init updates hold the apt lock for several minutes.
- **Worker 2's crash loop (probable).** kube-proxy on that node was still pulling its own image slowly, so the service IP Cilium needs wasn't working yet. It cleared once kube-proxy came up *(not verified with logs)*.

## What went well

- **Narrowing by elimination.** "Ping works but wget doesn't" ruled out routing and DNS and pointed straight at IPv6.
- **Reading events and conditions.** `kubectl describe` events and node conditions gave the exact stage of every failure.
- **No destructive shortcuts:** the dpkg lock was waited out, not deleted.

## Where we got lucky

- **Worker 2 recovered by itself.** Its root cause was never confirmed, so it could come back.

## Lessons

- **When one symptom has several faces, look for a shared cause.** Three separate-looking problems were the same one.
- **"Works with one tool, fails with another" is a strong clue.** Compare what the tools do differently: here, address-family preference.
- **Distributed systems often heal by retry.** Before intervening, check whether the system is converging on its own, and still find out why it failed.
- **A mitigation is a change.** Check its blast radius as carefully as any other change.
